## Decisions

- **Own table.** No generic operations table exists on master, so `task_delete_jobs` is added with the `CREATE TABLE IF NOT EXISTS` pattern. Results are one JSON document per job, rewritten after each task.
- **Ordering.** Preflight, stop, delete record, then git cleanup, with the worktree/branch/repo snapshot persisted before the record is deleted. A failed cleanup therefore leaves `record_deleted:true` and `failed`, matching the ticket's result shape, and a restart can finish cleanup without the row.
- **Restart safety.** A task not yet record-deleted is re-run from preflight (all steps idempotent, preconditions re-checked). A record-deleted task only repeats cleanup, and cleanup skips any worktree or branch a surviving task now references, so path reuse cannot lose a newer task's files.
- **Skip reason in `error`.** Skipped results carry the code in `error`, which the contract leaves as a string-or-null field.
- **Remote branch.** A repo without an `origin` remote reports `remote_branch: not_applicable`; an unreachable remote reports `failed`.
- **Duplicate ids are rejected** with 400 rather than deduplicated, since the contract asks for unique ids.
- **Sequential per job.** Tasks run one at a time; the per-repo lock still serializes overlapping jobs.
- **No deviation** from the ticket contract beyond the choices above.

- **Checkpoint failures.** Stop before mutation when the snapshot cannot be saved. Stop advancing the job on later save failures so the last durable snapshot remains recoverable.
- **Ownership fence.** `CreateAndStart` holds a cancellable flock-style file lock through creation, persistence and unwind. The lock lives under `db.DataDir()/locks`, is keyed by the canonical Git common directory, and is shared by TUI and daemon processes. Lock files are retained so concurrent waiters never split across different inodes. Cleanup holds the same fence while reading `TasksChecked` and deleting Git resources. The cleanup mutex is nested below the fence, its checked acquisition is cancellable, and no DB mutex is held across Git operations.
- **Containment.** Checked cleanup resolves paths against the actual managed roots and requires Git worktree registration in the expected repository. It uses Git removal without the legacy recursive fallback. Existing TUI cleanup helpers retain their behavior.
- **Shutdown and deadlines.** Delete jobs use a server-owned context. Every checked Git subprocess has a 15 second deadline and cancellation kills its process group. Shutdown cancels jobs, prevents new acceptance, and waits up to five seconds. Daemon cleanup shuts down the API before detaching the supervisor or event sink.
- **Progress publication.** Recovery checkpoints persist independently of events. Only status, completed or total changes publish job progress.

- **Confirmed stop.** Capture the session handle before Stop and wait up to ten seconds for process exit before any destructive operation. In-process runners use the original handle's Done/Alive state and reject replacement or pending restart. The daemon client confirms exit and absence of a queued restart over existing RPCs so a lost stream never counts as exit. No wire or supervisor protocol changes are needed.
- **Startup selection.** A Pending task is skipped as `task_creation_in_progress` only when a non-blocking probe cannot acquire its creation ownership fence. Pending status and zero StartedAt also describe settled failures and never establish creation activity by themselves.
- **Shared repository identity.** Canonical Git common directories identify shared refs, including projects configured from linked source checkouts. Worktree paths still compare filesystem identities for symlink and case aliases. Identity lookup errors fail closed.
- **Dirty check lifetime.** The dirty check uses the same bounded, process-group-aware Git runner as checked cleanup. Unless allow_dirty is set, check at admission and again after confirmed exit under both guards, before any log, artifact, record or Git deletion. Post-exit dirty or failed checks persist a skipped result and preserve resources; the stopped session remains resumable. At both admission and post-exit checks, only a not-found stat error may proceed; every other stat error skips with dirty_check_failed.

- **API mutation ordering.** `/resume`, `/restart` and bulk deletion share the API server's refcounted `taskLocker` with archive and input, acquired before task lookup. Cancellation uses the same lock entry and releases its reference. Deletion holds that guard through cleanup. Fresh deletion acquires repository ownership and validates relevant cleanup inputs before removing the row, then revalidates under the same ownership hold without recursive acquisition.
- **Last session check.** Immediately before Git cleanup, recheck live handles, locally visible startup reservations and queued restarts. Supervisor clients use authoritative status/restart RPCs, not cached output stream state. Presence reports `session_appeared` with resources preserved; failed RPC checks also preserve resources.
- **Scope boundary.** Full lifecycle exclusion is deferred to `serialize-full-task-lifecycle`, including non-API startup, account-move restart and ambiguous supervisor Start completion. The API guard plus one final presence check does not exclude those future starts.
- **Relevant owners only.** Check canonical worktree identities for every survivor, but resolve repository identities only when Branch or normalized BaseBranch could protect the target branch. Pre-deletion validation failures preserve the row as well as Git resources.
- **Exited Git leaders.** Always terminate the original Git process group before returning, even when the leader exited and CombinedOutput reports ErrWaitDelay. Output timeout makes the relevant cleanup stage failed; a ref may already have been removed, which remains an explicit partial-failure result.
