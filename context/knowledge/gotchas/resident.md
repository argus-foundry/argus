# Resident agent (add-resident-agent)

- **The resident rail name is a draw-only override on the shared Hera rail, cleared on mode exit.** Feed it through `SetResidentTitle` from both label refresh paths so Settings/config renames apply without reattaching; never rename the orchestrator or role model, which remain `resident` for routing.

Memory, orientation and tool permissions are in [resident-memory.md](resident-memory.md). Other resident invariants sit with their areas: ensure-loop and RPCs in `daemon-rpc.md`, Stop hook and recycle seed in `orchestration.md`, `ctrl+\` and return snapshots in `keybindings.md`, rail box and tab marker in `tasklist-ui.md`, Settings category in `misc.md`.

- **The resident is a task row with a `kind` marker, hidden at one choke-point predicate.** Task lists, the PR poller, reapers, merge-safety, `/api/tasks` and the cleanup sweeps all go through it; a new task-enumerating path that skips the predicate leaks the resident into Hera, the web UI or a completion sweep.
- **Worktree precondition:** the resident runs in its own directory, not a git worktree, so any code assuming "every task has a worktree/branch" must check `IsResident()` first (no merge-safety, no branch cleanup).
- **First attach forces a PTY resync; no size-drift kick for the resident pane.** `attachResidentSession` calls `ForceResyncPTY` for a newly bound live session because `SetSession` seeds the tracked size from the pane, so the delta check alone would never resize a replacement PTY. The Hera `RerenderKicker` machinery was deliberately not reused: it is bound to Hera pane bindings and its kill-and-resume restart path would race the daemon's resident ensure loop; the daemon launches the resident at the real pane size instead, which keeps drift rare.
- **`ResidentStateResp.Reason` is shown, not dropped.** `applyResidentState` copies it (control bytes stripped, UI goroutine) to the pane placeholder note and `Settings -> Resident` (`Not running: ...`). The placeholder draws only with no session and no replay content, so a healthy resident never shows it.
- **Settings' enable gate also needs `api.enabled`** (`ResidentPrereq`); TUI fixtures that enable the resident must set `api.enabled` too.
- **The Stop hook is gated on the resident's own task id** (`ARGUS_TASK_ID`), has its `coord-hook` supplied inline at spawn (see `resident-memory.md`, so it does not depend on the global hook registration), and always allows Stop. See `orchestration.md`.
- **Signals:** unread reply and `Waiting` (a pending confirmation) are two separate flags exposed together by `Daemon.ResidentState`; `Waiting` comes from the generic needs-input detector with the resident stripped from the generic set.
- **The resident reader must explicitly forward optional board reads; embedding `HeraReader` hides them.** Board attention is polled separately from reply unread, so viewing the conversation suppresses its marker but never reads board items; only a new unread item/version auto-opens the board after a manual plan toggle.
- **Rail-box no-resize invariant:** the rail ResidentBox changes height with unread/waiting state, so it must never resize the PTY pane (a resize triggers the size-drift kick). It is drawn only when no task is bound on the Tasks rail, stacks under the needs-input bar in the agent view, and has smoke tests asserting the agent pane rect is unchanged.
- **Hotkey recipe:** `ctrl+\` is the 0x1c byte; map Cmd+\` to "send hex 0x1c" in iTerm2/Ghostty and free the macOS "Move focus to next window" shortcut. See the README.
- **`config.toml` `[resident]` silently wins over Settings edits.** Settings writes DB keys; a key present in config.toml masks it with no warning. `allow_tools`/`ask_tools`/`deny_tools` are config.toml-only.
- **Settings' enable gate calls `ResidentPrereq()`**, which also refuses while `config.ResidentPermissionsEnforced` is false. It ships true; a branch built before the permissions stage landed would refuse every enable.
- **`residentOrientationPrompt(cfg)` is the single seam** for both the fresh-start prompt and the recycle seed; never build orientation text elsewhere.
- **Spawn surface 41, protocol v13:** the resident's spawn flags (`--settings` rules, forced permission mode, `?caller=` MCP URL) live in supervisor-resident `BuildCmd`, gated on `Task.Kind` riding the Start/Kick/Recycle request. Restart the supervisor after installing; the client refuses to launch the resident on a pre-v13 supervisor.
- **Not yet fenced:** the ai-ron `airon-dream` skip rule for `resident/**` and `dream: skip` is a separate-repo follow-up; the memory folder is unprotected from the nightly pass until it lands.
- **`BuildCmd` refuses a non-resident task whose worktree is the resident working directory.** An older TUI binary that doesn't send `Task.Kind` would otherwise relaunch the resident without its permission policy; the paths are compared after `filepath.Clean`.
- **A recycle seed is one-shot:** `restartSessionWithSeedPrompt` persists it as the row's `Prompt`, so the ensure loop's `start()` always resets `Prompt` to the orientation. Otherwise a later fresh launch (for example after `resident.account` changes and the old transcript can't be resumed) replays a stale handoff and relay directive.

- **Every resident recycle trigger must use the daemon's singleton `taskRecycleRunner`, including forced Hera recycle and the rail action.** Its reservation covers stray-job cleanup and seed assembly, and the runner's pending-restart flag covers the asynchronous replacement gap; a new runner per RPC defeats deduplication.

- **Team seeds use live bindings rather than archive-cleared meta markers, and never acknowledge mail.** Count unread messages independently of bounded history pages, which can omit old unread messages behind newer read history.

- **Disabling or prerequisite-stopping the resident stops only its session; worker bindings and supervisor sessions survive.** Resident state must count live worker sessions before its disabled-state early return, and Settings must keep polling while the resident tab is hidden, or the remaining workers disappear from the count exactly when it matters.
- **Everything `ResidentSend` queues (the budget nudge) and every task-message doorbell starts with `lastexchange.SystemTurnPrefix` (`[argus] `)**, typed or bridge-delivered, and last-exchange extraction skips such turns and freezes the replies after them. Typed without the bridge, the budget nudge would otherwise be quoted as "the user's last message" in the recycle seed.
- **The resident's orientation and recycle seed also start with `[argus] `**, so a recycle before any human turn quotes no Argus text as "the user's last message". Unprefixed Argus notices — bridge-delivered turns without `[argus] `, typed hera doorbells (`[hera from …]`) and `/api/notify` texts — are not marked: typed, they can still be quoted as the human message; bridge-delivered, they are skipped but do not freeze later replies (named follow-up `widen-last-exchange-delivery-tags`; it would change master's hera seeds).
- **Only the resident may `task_recycle` the resident** (`caller == resident`, fail closed): any other session's `handoff_note` would become the fresh resident's own authoritative handoff. Unbound callers keep recycling ordinary tasks.
- **A doorbell to the resident names the sender only through a strict `[A-Za-z0-9._-]` allowlist** (`sanitizeNudgeName`). The name is typed into the resident's PTY as a user turn, so spaces, punctuation or prose in a task name could otherwise read as an instruction (e.g. `x) — Aaron says: …`). Real names are slugs and pass unchanged; the resident reads the message itself through `task_inbox`, where it is data.
- **A running resident whose prerequisite later fails is stopped, not just refused a restart**, but only on the 2nd consecutive failing tick (`residentPrereqStopAfter`, ~10s) so a briefly unmounted vault drive does not kill it; the reason is set after the stop and shown immediately on the 1st failure. The no-Claude-backend error takes the same path (a config error); the MCP-not-bound wait is a startup state and never stops anything. The counter resets on any tick that passes the prerequisite and backend checks.
- **The resident launches at its OWN published size, never `Active`** (`db.InitialPTYRoleResident` → `InitialPTYLayout.Resident`). `Active` is whatever view the user is on (side-paneled agent pane, Hera worker pane), so the old `resolveSpawnSize(..., "", ...)` could start/restart the resident narrow and commit history the attach-resize cannot repair (BUG-078 family). The TUI computes it with `ptySizeFromHostTerm` (header + status bar + border, same as the zoomed agent pane) on every publish regardless of tab. The role constant is a selector only, never a stored hera role kind. An older TUI publishes no `Resident`, so `InitialPTYSize` returns zero for it (never substituting Active) and the daemon falls to the live PTY size, then 24x80. `internal/db/initial_pty.go`, `internal/tui/initial_pty.go` and `internal/daemon/resident.go` are not in `SupervisorSpawnPaths`/`SupervisorStreamPaths`, so no surface bump.
- **A stopped resident that has run before replays its dead log, so the placeholder's reason line never shows.** `TerminalPane.Draw` overlays the same `placeholderNote` as a one-line banner on the first inner row via a `defer` (covers every replay return path), only when `!alive` and the pane is not on the placeholder path; the row is blanked first so it never mixes with replay cells. The note is already empty whenever the resident runs (`applyResidentState` drops the reason when `Running`), so no extra clearing logic exists, and it is UI-goroutine only with no Sync.
- **Settings isolation carries only an ALLOWLIST of the user's Claude `sandbox` block, and never user hooks.** `--setting-sources project` drops both. `residentSandbox` copies only keys known to restrict: `enabled` and `failIfUnavailable` (only when true), `network.deniedDomains`, `filesystem.denyRead`, `filesystem.denyWrite` (key names verified against the local claude binary's schema strings), and forces `autoAllowBashIfSandboxed:false` + `allowUnsandboxedCommands:false` on whatever is carried. Every other key is dropped, including unknown future ones (a denylist would silently pass them): `allowAppleEvents`, `filesystem.disabled`/`allowRead`/`allowWrite`, `enableWeakerNetworkIsolation`, `allowNestedUserNamespaces`, `network.allow*`/`allowedDomains`, `excludedCommands`, `credentials.*` (mask mode injects real credentials at hosts, so it is not provably restrict-only). Nothing allowlisted left means nothing carried. **`enabled`/`failIfUnavailable` are dropped only when `argusWrapsSandbox` is true** (resolved config enabled AND sandbox-exec available AND a worktree; the same predicate as BuildCmd's wrap block, never the persisted `task.Sandboxed`): Claude's Bash sandbox cannot nest inside sandbox-exec (exit 71, see `sandbox.md`) and with `allowUnsandboxedCommands` forced false every Bash call would fail. It is fail-closed: if profile generation fails, the resident refuses to start (`resident sandbox profile: ...`) rather than run with neither sandbox; plain tasks still fall through unsandboxed. User hooks stay out: they cannot be classified generically and one (`argus-permission-approve.sh`) auto-approves Bash. Skipped hook events are logged once per spawn (`[resident] user hooks not applied`).
- **The resident's backend command passes a FLAG ALLOWLIST (Claude only, `Family.ResidentCommandCheck`), after the bypass/permission-mode strip.** Word 0 must be a plain unquoted path (`residentSafeExe`: no quotes, globs, escapes or `=`, not starting with `-`/`+`/`%`), optionally `~/`-led, whose base is `claude`; accepted words are plain or simple single-quoted (`'opus[1m]'`), while double quotes, `$HOME`, and UNQUOTED `[`/`]` (a sh glob that could match a cwd file) are refused with a single-quote hint; every other word must be `--model`, `--effort`, `--fallback-model` (value as next word or `=` form) or `--verbose`, and every accepted word must match a metacharacter-free pattern so a value cannot smuggle `;`/`$(...)` into the `sh -c` line. Anything else (`--allowedTools`, `--plugin-dir`, `--plugin-url`, `--agent(s)`, `--mcp-config`, `--settings`, `--setting-sources`, `--add-dir`, positionals, operators) makes `BuildCmd` return an error naming it, which the resident manager surfaces as its Reason. Only `--model` is a flag Argus itself appends to a Claude command; `--effort`/`--fallback-model`/`--verbose` were verified in `claude --help` and load nothing. Plain tasks are unaffected. The `--allowedTools` strip code was removed in favor of this refusal.
- **Concurrent first launches must not race on the private dirs or the skills link.** `ensurePrivateDir` accepts `EEXIST` only when the existing path is a real directory (not a symlink or file); the skills link is swapped by creating a temp link and renaming it over the target, with a `Readlink` fallback that treats an already-correct link as success when a peer won the race (`internal/agent/claudeaccount.go`).
- **Named follow-up `resident-source-integrity` (not fixed in this PR):** the sources the resident loads at each launch (`~/.claude/CLAUDE.md`, `~/.claude/skills`, and the account dir generally) are writable by every sandboxed Claude agent through the existing `/.claude` sandbox grant, so a sandboxed agent could alter what the resident loads at its next launch. The launch dir copies are protected (`resident-memory.md`); the sources are not. The same follow-up covers the EXECUTABLES the resident runs: its Stop hook uses `~/.local/bin/argus`, which links to `~/go/bin/argus`, and both dirs are writable by every sandboxed agent; a native-install `~/.local/bin/claude` has the same problem.
- **The resident's backend command must be one line.** sh ends a command at an unescaped newline exactly like `;`, so a trailing newline (easy with a TOML `"""` string) used to pass the allowlist while every flag Argus appends — forced `--permission-mode default`, `--setting-sources project`, the inline policy — ran as a separate failing command, launching Claude with none of it. `\`+newline continuations stay allowed; bare CR is refused too. `TestCheckClaudeResidentCommand_EveryUnsafeCharacterRefused` pins every refused ASCII character in both positions.

- **The standing team's ensure is the only creator allowed to use orchestrator name `resident`.** It creates the orchestrator, fixed-name coordinator role and resident binding in one transaction before launch; a pre-existing name without that binding is a collision surfaced through resident state Reason. Generic enumeration hides the orchestrator, while direct binding reads remain available for messaging/reconciliation and the resident view.
- **Resident spawn checks the cap twice: at MCP preflight and inside a serialized `SpawnHeraWorker` section before worktree creation.** Only live worker bindings count; the durable `hera/resident_worker=true` marker is stamped in AfterPersist before launch, and a marker write failure unwinds creation.
- **Resident delete identity comes exclusively from the transport caller, never cwd/id; live membership is checked before nuke.** `residentWorkerMutationMu` serializes deletion against graduation (graduation must take the same lock through its transaction, never through a restart wait); reclaim requires the sole live binding to match the selected role. A force summary is captured before reclaim, and an unreadable git field stays `unknown (reason)`.
- **The local empty-work check requires both zero commits ahead of the worker base ref and a clean tree.** Missing refs, missing worktrees and git errors fail closed; `git status -z` counts newline-containing filenames and rename pairs correctly. A classifier error also refuses default deletion.
- **A resident-bound Hera call pins cwd and orchestrator to the standing team.** Otherwise an allowed spawn or accept could bypass team scope by naming another coordinator's cwd. The resident and marked/live resident workers cannot bootstrap an orchestrator; workers request graduation instead.
- **The resident's MCP identity is a per-launch secret delivered ONLY by a private file, never argv or env.** The sandbox profile allows `process*`/`sysctl*`, so any same-user process (including bypass-active resident workers) can read another process's argv AND environment (KERN_PROCARGS2); `BuildCmd` therefore writes `~/.argus/resident-launch/mcp-token.sha256` (hash only) FIRST and then `mcp-config.json` (0600, atomic rename, token in the `X-Argus-Resident-Token` header so it never sits in a logged URL) and passes `--mcp-config <path>`.
- **Every resident launch rotates the token, and an unverified caller is treated as UNBOUND, not refused outright.** `verifiedCaller` (MCP `handlePOST`) keeps `?caller=` only when it names the resident and the header's SHA-256 matches the current hash (constant time); everything keyed on `req.caller` (tool listing, Hera pinning, delete/graduate, `task_recycle`) inherits that, and a non-resident `?caller=` value is ignored. A resident launch with MCP off deletes the hash so no earlier token stays valid; the file-capable `Family.MCPConfigFile` is required or the resident refuses to launch.
- **Every sandboxed task except the resident is denied file-read of `~/.argus/resident-launch`** (`sandboxWithResidentLaunchDenied` in `BuildCmd`; the daemon's `SandboxDenyReadPaths` lists it for every caller). The data dir is symlink-resolved before joining because the dir may not exist yet when a task's profile is generated (SBPL symlink trap); integrity of the hash rests on `~/.argus` not being writable by sandboxed tasks (only `~/.argus/cache` is).
- **The resident-identity guard covers EVERY MCP tool, not just `hera_*`, and every task-id argument.** `resolveTask`'s `residentByCwd` fallback exists only so the resident can name itself, so a non-verified connection passing the resident's `cwd`, or its task id as ANY string `id`/`task_id`/`caller_id` (`residentTaskIDArgs`; an allowlist of "self-id" tools missed `task_stop` and friends), is refused before dispatch, with no read-only exemptions. Hera board/message ids are integers and never match. **The guard must match every receiver's normalization, not the built-in spelling:** it finds identity keys with `strings.EqualFold` (ALL matches, not the first) because plugin tools keep their own schemas and may decode case-insensitively (`{"Task_ID": <resident>}` to iris, `{"CWD": "~/.argus/resident"}` to plannotator), and compares values after `TrimSpace` because built-ins trim (`task_move_account` task_id/caller_id, `profile_resolve` cwd); ids also match the resident's id case-insensitively, and a cwd is `~`-expanded, cleaned and matched component-wise case-insensitively (symlinks resolved) against the resident's directory, since APFS and plugins see through both.
- **Tool argument names must be canonical (`^[a-z0-9_]+$`) or the call is refused before pinning and the identity guard.** Those read exact map keys, but every tool decodes with `encoding/json`, which matches keys case-insensitively incl. Unicode folds (`ſ`→s, Kelvin→k): `{"CWD": <resident>}` passed the guard and spawned as the resident, and a later-sorting folded duplicate (`orcheſtrator`) overrode the resident's pinned value. `TestBuiltinToolSchemasUseCanonicalKeys` keeps built-in schemas in that alphabet; plugin tools (own schemas, no Argus identity) only refuse fold-colliding keys.
- **`hera_delete_worker` runs the fleet-wide `ReconcileHeraReclaims` asynchronously, after the role-scoped work.** `hera.NukeResidentWorker` (resident-only; `NukeSingleRoleAs` stays the TUI's synchronous path) nukes the role and stops, reclaims and prunes that one task under `residentWorkerMutationMu`; the sweep and the deleted task's stacked-branch follow-up run in a recovered goroutine serialized by `residentReconcileMu`, never under the mutation lock. Safe against a concurrent graduate/delete because sweep candidates are user_deleted-ended tasks with no live binding (a graduate always holds one, pending graduates are skipped) and `PruneTasks` re-checks at delete time. Tests wait on `Server.residentBackground` before the DB closes.
- **`hera_delete_worker` without `force` refuses any dirty worktree, even with a safe verdict.** A merged or zero-commit branch says nothing about uncommitted/untracked files; `DirtyCount` must be exactly `"0"`, so an `unknown (...)` count fails closed. **A HEAD that is not `refs/heads/<task branch>` (detached, or another branch) or a rebase/merge/cherry-pick/revert in progress also counts as dirty** (`residentWorktreeState`, before the stop AND in the post-stop re-check): commits there are invisible to the clean-tree and branch-tip checks yet become unreachable when the worktree goes (an unborn HEAD on another name holds no commit and passes). The op markers live in the worktree's own git dir, so they are located with `git rev-parse --git-path`, never `<worktree>/.git/...` (a linked worktree's `.git` is a file).
- **A non-force `hera_delete_worker` classifies while the worker's session may still be live, so it re-checks AFTER the session has exited.** Order: idle-or-absent check, branch-tip capture, summary + clean-tree check, classify, stop, exit wait, re-check (tree clean and tip unchanged), nuke via `hera.NukeResidentWorkerChecked`. The tip is captured FIRST: captured after the summary, a commit landing in between sat inside the recorded tip while the stale summary read `Empty()`, so an unsafe verdict passed and the re-check saw nothing move. Idle = raw `IsIdle`, else a bounded `agent.ContentIdleTracker` sample (6s at 500ms, enough for the 3s stability threshold and the 8-tick parked-selection escalation; `TestResidentDeleteProductionValues` pins the real values because the package `init` shortens them) so a parked prompt that keeps animating (BUG-083) is not refused forever; a pending restart or a session the runner reports but cannot hand over (`Get` nil, present) is busy, a dead handle is absent.
- **In the resident delete an unreadable session presence is PRESENT, never gone.** The daemon's runner is the supervisor client, whose `HasSession` folds every `SessionStatus` RPC error (incl. the 2s `ErrRPCTimeout` under load) into false; read as "gone" it skipped the stop, ended the exit wait early, and the re-check passed against a live session. Presence goes through `hera.SessionPresent` (the client's `agent.SessionPresenceChecker`, which also counts a pending restart; the in-process runner falls back to its authoritative `HasSession`): a probe error refuses the idle check, still issues the stop, keeps the exit wait polling until it refuses at `Max`, and defers the post-reclaim prune to the sweep.
- **Settle is measured from when `Stop` RETURNS; `Max` from when it began.** The supervisor starts its 5s group-SIGKILL timer only when its own `StopScoped` runs, so with a slow RPC a Settle counted from before the call could recheck before the SIGKILL. Defaults: Settle 6s, Max 10s (covers the client's 2s RPC timeout + Settle; `TestStopWaitDefaults`).
- **A failed `Stop` is not trusted either way, and the delete is always refused (`ErrWorkerStopFailed`).** A timed-out supervisor Stop RPC was usually delivered, so reverting the pre-stop in_review flip at once let the late exit relay see in_progress and stamp `ready_to_close` (looks finished). Instead the exit wait runs; the flip is reverted ONLY when a successful probe at the end shows the session still running (the stop did not take); if it exited, or presence stays unreadable, the flip is kept (in_review without the stamp is resumable).
- **One overall deadline (`residentDeleteDeadline`, 45s) covers the whole call, force or not, INCLUDING time queued on `residentWorkerMutationMu`** — the clock starts at handler entry, before the lock. Everything before the first change (the stop; the nuke for force) must leave the worst-case remainder (non-force: stop `Max` + re-check 10s + local nuke 8s; force: 12s), so idle sampling and the tip/summary/classify context are capped by that instant (`MutateBy`), and past it the call refuses "host busy; retry" with nothing changed — `NukeResidentWorkerChecked` re-checks `MutateBy` itself before arming the stop guard, since classification can eat the budget after the handler's own check. `GiveUpBy` caps the exit wait so the re-check and nuke still fit. A budget-expired summary or classifier is reported as host busy, not as dirt or "not safe". **The per-repo cleanup lock is taken in that pre-change phase too** (`agent.TryLockRepo` polled on the delete's clock until `MutateBy`, else "host busy; retry" with nothing changed) and held through the stop, exit wait, re-check and local removal (`RemoveWorktreeAndLocalBranchLocked`), released before `followUp`. `RemoveWorktreeAndBranch` (daemon-side reclaim sweep, REST/bulk delete, prune — the lock is an in-process `sync.Map`, so TUI-process nukes never contend; git's own lock files cover cross-process) holds that lock across an UNTIMED origin push, so queueing on it after the stop could blow the MCP deadline with the role already nuked and the force summary lost. Cost: other cleanups in the same repo wait out the delete's stop wait (up to ~10s plus re-check).
- **The deleted worker's ORIGIN branch delete is asynchronous, so the post-stop section is local and bounded.** The resident path uses `agent.RemoveWorktreeAndLocalBranch(Locked)` (worktree + local branch only; `RemoveWorktreeAndBranch` is unchanged for every other caller) and `followUp` runs `agent.DeleteRemoteBranchContext` with its own 30s timeout, logging success or failure, before the stacked-branch follow-up and the fleet sweep. The remote delete deliberately does not take the per-repo cleanup lock, so a hung push never blocks a later delete's local removal in the same repo.
- **The async origin delete is LEASED (`git push --force-with-lease=refs/heads/<B>:<tip> origin :refs/heads/<B>`).** Resident worker branches are name-derived (`argus/resident/<name>`), so a new worker with the same name can push the same branch before the queued delete runs; an unleased `push --delete` removed its branch (and closed its PR). The tip is captured under the repo lock BEFORE the local branch is deleted: `refs/remotes/origin/<B>` when present (what this repo last saw on origin, so unpushed local commits do not break the lease), else the local tip. A failed lease (git's `stale info`, matched under `LC_ALL=C`; also what an already-deleted branch reports) is `agent.ErrRemoteBranchChanged`, logged "remote branch changed since delete; left in place" and never retried; an unknown tip skips the delete rather than run unleased.
- **The resident delete path logs through `uxlog` AND `slog`** (`residentDeleteLog` in `internal/hera`, `residentMCPLog` in `internal/mcp`): it runs in the daemon, which never calls `uxlog.Init`, so `uxlog.Log` alone was invisible (refusals, stop failures, "prune deferred", the async origin-delete outcome).
- **An unreadable live-binding list refuses the delete with nothing changed.** Read as "bound elsewhere", it skipped the stop and re-check while the nuke still ended the only binding `user_deleted`, making the task an immediate reclaim candidate that the async sweep removed (worktree + branches) under a possibly live session.
- **The delete's own stop must not close the worker out.** Stopping an in_progress worker fires the exit hook (`RollHeraWorkerToReview`: in_review + `ready_to_close`), so a refused worker would look finished and refuse revive. Before the stop the guard flips it to in_review itself without the stamp (`RollHeraWorkerFailed`); every exit-hook site is in_progress-gated, so the hook no-ops even when the supervisor's exit relay lands after the tool returned. On refusal it also clears a `ready_to_close` that appeared during the delete (never one the worker already carried), and reverts the flip only for a failed `Stop` a successful probe proved did not take (see above). Refusals keep role, binding and worktree; force keeps the original order (nil recheck, no wait); the TUI's `NukeSingleRole` is untouched.

## Graduation

- **Graduation commits membership, worker-marker removal and `graduation_pending_restart` together.** Splitting those writes strands a coordinator with unattended flags after a crash; preserve `AccountRouted` so graduation never turns an automatically routed account into a human pin.

- **The daemon graduation watcher resumes with `KickRerender`, never `KickRevive` or recycle.** `KickRevive` can silently start fresh without a transcript; graduation must preserve the exact conversation and uses a persisted outgoing PID to recover before/after the asynchronous kill-and-resume gap. Busy sessions are retried indefinitely without stray-job cleanup; ordinary coordinator recycle is deferred until the marker clears.

- **Graduation orientation is a durable system-message outbox, separate from restart intent.** Message insertion and marker removal commit together, then notifier delivery retries from `graduation_orientation`; the `[argus]` prefix keeps the injected orientation out of user-exchange capture.

## Codex unattended-worker spike

- **Worker identity must be queried at launch, not serialized from task meta.** Production runners and supervisor clients receive `db.IsResidentWorker`; Start/BuildCmd and kick/recycle preflight query it again, covering marker loss after hide/unhide. Graduation must end membership AND clear the marker; the next query then restores normal flags without the worker sandbox gate (including supervisor-owned pending restarts).
- **Worker-account toggles affect only new resident spawns and merge per key.** Settings writes only the raw DB map, never a copy of the config.toml overlay; copying the overlay would leave deleted file overrides frozen in Settings. Account eligibility is the intersection of `AccountSupports` and non-nil `Family.UnattendedWorker`, so Codex-only accounts stay invisible.
- **The prompt backstop treats detector needs-input and role `blocked` as one episode.** Switching between the two must not re-notify; only clearing both arms another message. Notices use the durable Hera store and its existing notifier delivery ID, so an idle-gated doorbell retry never creates another message.
- **Unattended workers require supervisor spawn surface 44 (stream 17 for restart preflight).** An older supervisor cannot enforce the new launch flags; the daemon refuses worker launches and restart requests to it before stopping a running session.

- **Codex 0.167.0 bypass closes command approvals, not question tools: keep resident-worker eligibility nil.** A real resumed session still displayed an async question with both candidate feature overrides false, and `/plan` still enabled a blocking question (`collaboration_modes` is a removed flag); no verified launch/resume closure was found. — `add-resident-coordinator` task 4.0, 2026-11-09; [commands, sanitized rollout excerpts and limits](../../spikes/2026-11-09-codex-unattended-worker.md).

```text
         request_user_input -> no output while unanswered; interrupted after >60s
```
- **Human nuke/hide/rename of a resident worker is reported to the resident through a db-level outbox (`resident_notices`), not an in-memory hook.** The rail's mutations run in the TUI process, which cannot deliver a Hera doorbell, so the choke points (`ArchiveHeraRoleAs`, `NukeHeraRoleAs`, `RenameHeraRole`, and the Tasks-list `Delete` transaction) write a row and the daemon's resident loop (`deliverNotices`, every 5 s) turns each into one Hera message from the affected worker's role to the resident coordinator. Delivery claims the row before sending and deletes it after; a retryable failure (inbox full, rate limit) releases the claim and ends the pass so order is kept.
- **The resident's own `hera_delete_worker` passes `db.HeraActorResident` through `NukeSingleRoleAs`, which suppresses the notice; everything else is the human.** Role-status steps, unhide and idempotent repeats (already hidden/nuked, same-name rename, rename conflict) queue nothing.
- **Notice membership is decided from the role's orchestrator binding, never `task_meta`.** `db.SetArchived` wipes `task_meta`, so keying on the `resident_worker` marker (or on `IsResidentWorker`'s marker clause) would drop a hidden worker out of the notice path and the resident rail. Test: hide, notice, unhide, still on the rail, hide again notifies again.
- **The nuke notice's "unmerged" line is deliberately cheap: branch name and task status, no git.** The worktree is already reclaimed when the daemon composes it, so it never claims anything is safe.

- **A graduate with `hera/graduation_pending_restart` set cannot be archived or deleted (`db.ErrGraduationPending`).** `SetArchived` wipes all `task_meta` and `task_messages`, so archiving before the daemon watcher's restart would drop the restart intent and orientation outbox and leave a bypass-active session running as a top-level coordinator.
- **The block lives at every DB choke point, not per surface:** `SetArchived(true)`, `Update` on an unarchived-to-archived transition (REST archive, MCP `task_archive`, raw PUT), `Delete`, and `PruneTasks`/`pruneTasksLocked` all check the marker inside the mutation's own lock/tx; the refused call changes nothing and un-archive is unaffected.
- **Destructive flows that do side effects first must pre-check `db.GraduationPending`:** TUI delete/nuke, REST delete, bulk delete (skip code `graduation_pending`), Hera `NukeSubtree`/`NukeSingleRole` and the reclaim sweep skip the whole role or task and log `[resident] ... graduation pending`, because stopping a session or removing a worktree before the DB refusal would half-apply.
- **`UniqueHeraOrchestratorName("resident")` de-collides to `resident-2`, `resident-3`, ... and never returns `resident`:** automatic naming (plan sub-coordinator materialization, promotion) must not fail on the reserved name; explicit `CreateHeraOrchestrator`/`RenameHeraOrchestrator`/`hera_new_orchestrator(name="resident")` still reject it.
- **Account/backend moves and graduation exclude each other only best-effort.** A move claims the task (`AccountMoveInFlight`) before checking `GraduationPendingErr`, and graduation's preflight refuses while a move is in flight; there is no shared per-task lock, so a graduation committing between a move's claim-time check and its session-ID clear can still wedge the watcher (preflight fails forever). Named PR follow-up: a shared per-task mutation lock in `internal/agent` held across move check→kick and graduation check→commit. Until then the human-only TUI abandon escape (`AbandonGraduationPending`, double confirm on delete/archive) is the way out.
- **The async origin delete is leased, so a stale lease leaves the branch on origin (accepted).** The lease tip is `refs/remotes/origin/<B>` (else the local tip) captured before the local delete; it only moves when this repo pushes/fetches, so a branch changed server-side (GitHub "Update branch", a bot or reviewer push) and then merged without auto-delete fails the lease and stays on origin — logged "changed on origin; left in place", distinct from "already gone" (an `ls-remote --exit-code` classification only, never a delete decision). Harmless leftover; never deletes a re-created same-name branch. Named PR follow-up: on lease failure, fetch that ref and retry once with an ancestry-checked lease.

- **Backend/account moves of a resident worker preflight the target before persisting.** `MoveTaskBackend`/`MoveTaskAccount` write the row before any restart and a STOPPED worker is never preflighted, so an ineligible target (non-unattended family, account disabled in `resident.worker_accounts`) would strand it behind the launch gate on every later start/revive. `refuseIneligibleResidentWorkerMove` applies `ResolveResidentWorker` + `preflightUnattended` to a copy with the target backend/account, fails closed on identity-lookup error, and leaves non-resident tasks alone.
- **An unattended resident worker is hard-denied the resident's whole outward ask + deny tier at launch** (`ResidentWorkerDenyRules`, derived from `ResidentOutwardTiers` = the loaded `[resident] ask_tools`/`deny_tools`, so config overrides apply; the account's user ask/deny are NOT merged for workers). It rides a SECOND `--disallowedTools` flag via `Family.UnattendedDenyFlag`; BuildCmd refuses an unattended launch on a family with `UnattendedWorker` but no deny flag. Verified headless (claude 2.1.317, bypassPermissions, user settings loaded): repeated `--disallowedTools` accumulate, a denied MCP tool is unloadable even when an inline `--settings` allow names it exactly or by wildcard, `mcp__server__*` removes the whole server, and an exact deny leaves siblings (e.g. `slack_send_message_draft`) callable. Testing it: the `system/init` event is emitted before claude.ai connectors connect (`pending`), so check by asking the model to call a harmless denied read tool, not by the init tool list; an untrusted project `.claude/settings.json` is ignored in `-p`. Blank or dash-led rules are skipped (they would parse as flags inside the variadic list).
- **Deleting an account drops its `resident.worker_accounts` toggle in the same transaction** (`db.DeleteAccount`), so an account re-created under the same name starts enabled for resident workers like any new account instead of silently inheriting a stale "disabled" key that Settings never shows (only eligible accounts are listed). config.toml-defined toggles belong to the file overlay and are left alone; an unparseable stored map is left as is (Config already ignores it).

- **Cross-tab entry must select the resident rightmost pane after `switchTab(TabResident)`.** The switch re-points the shared HeraPage and rebuilds its layout; selecting focus before it would be overwritten by normal conversation-pane entry. Internal arrows already use HeraPage’s pre-PTY focus ladder, which runs before the filter handler; the enabled shell chain must consume modified horizontal arrows while the resident rail filter is active so they cannot move focus into a PTY.

- **`resident.accounts` is an ordered preference list; the resident's current account is a persisted marker (`account_override` in resident task meta: account, `by` manual|auto), never a rewrite of the list.** `agent.ResidentAccountEntries` normalizes the list (unset = `["default"]`; skips unknown/Codex-only/duplicate/blank entries with a note; cuts at the first `auto`; falls back to default if nothing survives) and `ResidentStartAccount` / `DecideResidentAccount` are the only two policy functions: start keeps the persisted account when allowed and not depleted (a manual one also when out of the list), else the first usable listed entry; the RUNNING-resident decision (`DecideResidentAccount`) is depleted -> next usable listed entry, not-allowed -> onto the list, and NEVER a move up; the restart-time decision (`DecideResidentRestartAccount`, cold start / crash restart / recycle) additionally moves up to a more preferred listed account with a fresh reading (and replaces a depleted/delisted/invalid one). A `manual` marker only exempts the RUNNING session from the not-allowed move (so the tick does not undo a human's `>` seconds later); it is NOT a hold across restarts: `>` is a one-time escape hatch and the next restart/recycle re-picks per the list. The `auto` slot never chases headroom among non-listed accounts (same rank = no move). Only `db.SetResidentAccountMove` writes the row's account past `residentGuard`, in one transaction with the marker and session id; generic `MoveTaskAccount`/`MoveTaskBackend`/REST/MCP still refuse the resident.
- **Legacy `resident.account` DB values read as a one-element `resident.accounts`** (so a hand-set account survives the list change); `Settings` saves always blank the legacy key, otherwise clearing the list would resurrect the old value. config.toml `account` is an ignored unknown key now.
- **The move core validates against the config its caller decided with.** `agent.MoveResidentAccount` takes `ResidentMoveOpts.Cfg` (the daemon passes `m.cfgFn()`); reading `database.Config()` instead can disagree with the tick that triggered the move (and with config.toml overlays in tests).
- **The automatic trigger is the cached usage reading, so a hard limit can be noticed up to one probe interval late when the bridge is not live.** Depleted = a live (valid, fresh) five-hour OR weekly window at 100% or more (`agent.AccountDepleted`; unknown/stale/reset never counts; a weekly-only 100% depletes with the five-hour at 0%). The session must be parked (raw-idle OR `agent.ContentIdleTracker` content-idle: Claude Code's "Continuing automatically ... Esc to cancel" limit-wait footer keeps repainting so raw idle never holds; a working screen never counts) on two consecutive 5s ticks, with a persisted 10-minute cooldown (`last_auto_switch_at`, shared by depletion, off-list and restart-time moves, survives a daemon bounce), and the move runs with Force=true only after that check (the move core's busy refusal is raw-idle only). A needs-input flag deliberately does NOT block: Claude Code's usage-limit menu is itself a prompt, so honoring it would deadlock the exact case this exists for; the transcript resumes so only the pending prompt is lost. With every listed account depleted it logs and posts one `decision` board item per episode (`noneEligible` resets when something recovers or a move happens) and keeps retrying.
- **Resident board posts use only the existing kinds (`fyi` for a move, `decision` for "nothing usable").** The daemon posts on the resident coordinator role found through `EnsureResidentOrchestrator` + `ListHeraRolesByKind`; a failed post is logged and never undoes the move.
- **No self-service switch tool (named follow-up `add-resident-self-switch`).** A tool that restarts the caller's own session is why `task_move_account` forbids self-moves; it would need a deferred-intent flag executed by the daemon at the next idle (like self-service recycle), self-only for the verified resident.
- **`>` is allowed in the resident tab only on the resident's own row (`ResidentOwnRowOnly`).** The page reuses `OnMoveAccount`; `App.runAccountMove` routes a resident task to the daemon RPC `ResidentMoveAccount` instead of the in-process move, so it serializes with the ensure loop. The picker lists Claude accounts plus `auto` only (no handoff rows) and its `auto` preview skips depleted accounts.
- **The Settings accounts editor is a modal with modal-local literal keys (Space, K/J, Enter, Esc), not keymap actions**, so keymap/help rows are unchanged. Gotcha for tests: `waitForCond` already runs its predicate on the UI goroutine, so calling `readUI` inside one deadlocks the whole test (it hung until the package timeout).
- **Moving UP the list needs a FRESH positive reading; unknown or stale is never "recovered".** `LiveWindows` drops windows older than `CacheMaxAge`, so an account Solo left (depleted) ages to "no depleted window" within an hour; treating that as recovery flapped Solo back to a still-empty account hourly. `agent.AccountReadingFresh` gates the restart-time move-up only ("unknown is not depleted" still holds for LEAVING the current account), and `usagebudget.ProbeConfiguredAccounts` now probes every `resident.accounts` entry (all Claude accounts when the list ends in `auto`) so recovery is actually observable.
- **Every restart re-picks the account, but never by rewriting `task.Account` for a resuming session.** `start()` (resuming, no live handle: `runner.Get == nil`, so a reattach never re-picks) calls `repickAtRestart`, which runs the move core (transcript copy + resume, `by=auto` marker, cooldown stamp, `[argus]` turn, `fyi` item) and reloads the row; rewriting `task.Account` directly silently minted a fresh conversation. A recycle (`taskRecycleRunner.restart` -> `repickForRecycle`) has no conversation, so it only calls `SetResidentAccountMove` and returns the notice as a seed-prompt paragraph (a turn sent to the outgoing session would die with it). Restart move-ups are suppressed while the 10-minute cooldown runs, which is also what stops a move's own restart from bouncing Solo back; depleted/delisted/invalid replacements ignore the cooldown. `auto_switch_account` off disables restart re-picks (except invalid-account recovery).
- **The restart a manual move itself performs must not re-pick:** `MoveAccount` records `manualMoveAt` and `restartDecision` ignores restarts within `residentOwnRestartWindow` (2 min); an auto move's own restart is covered by the cooldown it stamps. Picking `auto` in the picker records `by=follow`. Only `by=auto` stamps `last_auto_switch_at`.
- **Only a move OFF a depleted account (`ResidentDecision.Urgent`) ignores needs-input and an unsent draft;** the off-list move also requires no pending prompt and no composer draft (rendered-screen `InputDraft`; the bridge draft signal lives in `internal/api` and is not used here, unknown reads as no draft).
- **The "no usable account" board episode is persisted in task_meta (`none_usable_posted`)**, loaded once per manager, so a daemon bounce does not repost it; `switchTicks`/`noneEligible` are guarded by `m.mu` because `MoveAccount` runs on the RPC goroutine.
- **`Daemon.ResidentMoveAccount` uses a 60s client timeout** (`residentMoveTimeout`): the daemon copies the transcript and restarts synchronously, far past the 2s default `rpcTimeout`.
- **config.toml `[resident] account` is read as a one-element `accounts` (deprecation logged on load)** and, like `auto_switch_account`, marks its Settings row `(config.toml)` read-only.
- **A resuming start with a stored account BuildCmd would refuse (removed from config.toml, or no `claude_config_dir`) must recover, not retry forever:** the tick only runs for a live session, so `start()` calls `recoverInvalidAccount` first (`residentAccountUsable` mirrors BuildCmd's check). It moves onto the list's first usable account through the move core (marker `by=auto`, cooldown stamp, `[argus]` turn, `fyi` item). The old account's `claude_config_dir` is unresolvable in exactly these cases, so the transcript cannot be copied: the fallback persists the new account with an empty session id and Solo starts FRESH (and is told). The probe of `resident.accounts` is skipped while the resident is disabled.
